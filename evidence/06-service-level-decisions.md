## 2. 五个决策（已答复）

### 决策 1：普通体检是否必须一次查到完整结果？

**答复**：**必须一次查到完整结果；最多允许残余 20% 的剩余地段。**
不满足时**保留结果并明确标为未达标**，同时提供**"重试"入口继续推进**；
文案按**实际原因**区分（真实超时 / 本轮请求额度用完 / 今日额度用完），不统一写成"请求超时"。

**"残余 20%"的口径（需澄清后确定）**：以**本次体检原圈面**为分母，
**所有所选小类共同完成检索**的面积至少占 **80%**。
即：把各小类"未完成区域"取并集后再与圈面求比，而不是各小类各自达标
—— 后者会让"某一类完全没查、其余各类都查完"的平均数掩盖掉整块空白。

**边界（写进验收）**：
- 这里说的"完成"是**检索证据完成**，不是"现实中所有设施都已找到"（`catalogCompleteness` 永远是 `unverified`）；
- 查询缓冲区不计入分母；圈面上的孔洞/多部件按实际几何计算；
- 成功返回的"无匹配"是完成，**缺页不是**；
- 旧修订没有该指标时显示"未记录"，不反推。

**与额度的关系（本轮已解决）**：上调后单任务 240 可覆盖"适中"（203）；
"密集"（1379）仍超单任务上限，因此**重试路径是达标的必要能力**，不是可选项。

### 决策 2：同一地理位置"新建体检"是否应复用前一次的数据？最大数据时效？

**答复**：**允许复用**（以降低等待时间）。**最大时效 = 决策 1 之外的"会话+次数"期限**（见下）。

**期限（L2/L4）**：两个条件**任一先到即过期**：
1. **用户关闭浏览器** —— 落实为"本应用最后一个标签页关闭"，允许最多 **5 分钟**的检测宽限
   （刷新、短暂断网、多标签页共享会话都不应误清）；
2. **该次体检之后的第三次新体检结束** —— 失败/取消的新体检也计数；
   幂等重发、重试、补查、新修订**不计**新体检。

**补充口径**：
- **复用不重置来源期限**：第 1 次的数据用于第 4 次报告时，它在第 4 次结束时已到期，
  对应的 POI 明细一并从后续报告中清除（允许保留不含明细的汇总与到期提示）。
- **期限同时覆盖缓存与含明细的报告**，不只是内存缓存。
- **现有历史数据**：已经落盘、没有会话归属的历史报告视为**已过期**，
  一并清除 POI 明细，保留不含明细的汇总与清理记录。
- 现行 `cache_freshness_seconds`（固定秒数）**不足以表达这个期限**，需要会话与计数实现。

### 决策 3：是否要求应用重启、跨日、跨进程仍能续查？

**答复**：**不要求。**
（现状已满足"重启后仍能看到已完成的部分"——修订是不可变 JSON，重启不删除；
但这不等于续查。）不进入 F 阶段，不实现持久化查询状态。

### 决策 4：核心三类与其余七类的最低覆盖要求、可接受的最大真实网络预算？

**答复**：**暂时没有改变**（类别口径不变：核心三类默认勾选，其余七类按需）。
最低覆盖要求由决策 1 的 **80% 共同完成面积**给出。
可接受的最大真实网络预算：**按第 5 问的 40% 口径**，并已授权把应用自身额度上调到
单任务默认 240 / 上限 1600 / 每日 2000。

### 决策 5：是否允许少量经批准的真实 Place API 对照实验？

**答复**：**允许。**
- **总次数**：不超过账号 api 限额的 **40%**；2026-10-09 追加指示**取消原暂定的 32 次**
  （"太抠门"）。按 5 万次/天，40% = **20000 次/天**。
- **区域**：**上海市**（与本地路网包 `geofabrik-shanghai-260913` 相适配）。
- **其余（停止条件、日志边界）**由本方案给出并执行，见 §5。

**必须说清的一点**：实验走**同一个服务池与同一个日账本**，
所以真正生效的上限是**应用日预算 2000**，不是 20000。
"40%"是运营授权天花板，不是本批次会花掉的量。

## 5. 从这些决策推导出的实现要求（供 C/D 阶段排期）

这些是**决策的后果**，不是新的决策：

1. **覆盖率指标**：新增 `queryAreaCoverage`（原圈面面积、共同完成面积、剩余比例、`met/unmet/unknown`），
   在既有米制投影里把各小类未完成区域取并集后裁剪到圈面；重叠不重复扣减。
2. **同一次体检的重试**：新入口 + 独立本轮预算（默认 240、上限 1600）；
   冻结原圈面与类别，复用缓存只为缺页付费；发布新修订；重复标识取回同一次操作，
   参数不同 409，同一体检禁止并行发布重试修订。重试**不计**入决策 2 的"新体检"计数。
3. **会话与生命周期**：会话注册/续租/离开；来源期限随派生数据传递；到期先标记不可访问，
   再取消相关工作、阻止迟到响应回写，最后删除受管明细并另存白名单摘要；
   历史数据迁移先生成清单再执行。
4. **文案**：按真实停止原因区分（超时 / 本轮额度 / 今日额度），并显示覆盖率与重试条件；
   含明细的响应加 `Cache-Control: no-store`。
5. **真实实验**：单批上限 = min(40% × 账号日权益, 可用日余额)，逐页计账、可随时停、
   上游报错即停；原始 POI 与 UID 只在进程内比较，落盘只留汇总。

**优先级**：第 4 项（文案/不落盘）与第 1 项（覆盖率）是决策 1 的最小可见交付；
第 2、3 项是决策 1/2 的核心能力。四项都必须在**任何真实实验之前**完成，
否则实验会违反刚取得的授权（`05` §4.1 也仍然阻塞）。

### 6.2 更正：80% 停止派发的真实口径（我先读错了）

**运营者 2026-10-09 澄清**：*"若超额了，而且已经完成了至少 80% 的进度，那么可以停止派发。"*

即：**停止派发的触发条件是"额度用尽"，不是"达到 80%"**；80% 是**在那一刻的验收线** ——
额度用尽时若已完成至少 80%，这一轮就算达标、干净收工，不需要重试；若不足 80%，
才交给决策 1 的重试路径继续推进。

**此前我把这条读成了"一到 80% 就收工"并写成本节的"偏离"，那是误读。** 按正确口径看，
现有实现**已经符合**它，不需要新增提前停止逻辑：

| 要求 | 现有实现 |
| --- | --- |
| 额度用尽即停止派发 | `OnlinePlanner` 的 `drain_after_budget_refusal` + 服务池在派发前最后一次原子裁定；被拒的页面按名字记账（`allowanceRefusedPages`），停止原因是 `network_budget_exhausted` / `daily_budget_exhausted` |
| 那一刻 ≥80% 就算达标 | `queryAreaCoverage.status = met`（比例 ≥ 目标），`queryStatus` 仍是 `partial` —— 两个口径分开报告 |
| 达标时不再要求重试 | 前端 `queryCoverageRetryLine()` 在 `met` 时返回 `null`，因此**不显示**重试建议；`queryCoverageLine()` 显示"达标（仍有查询未结束，已取得的证据保留）" |
| 不足 80% 时才重试 | 后端 `POST /api/v2/checkups/{taskId}/retries`；前端在 `unmet` 时给出按原因区分的下一步 |

额度还剩、但已经到 80% 时**不提前收工** —— 这与你说的"若超额了…可以停止"一致：那时没有
超额，就继续查完，多出来的证据是白得的。

**新增回归测试**（`queryCoverage.test.ts`）：`partial` + `network_budget_exhausted` + 85%
→ 判定达标、且**不给**重试建议。这条把上述口径钉在可执行的地方。
如果你本意确实是"到 80% 就不再花额度"，改动很小（在 `OnlinePlanner.run` 里加一个可选目标、
达标即收工），但那是**成本决定**，应当由你明确，而不是由实现顺手替你决定。

## 7. 会话与生命周期：实施记录（2026-10-09）

决策 2 的两条期限此前**没有任何代码在执行**（`05` §5 记为缺口）。现在它们是可执行的，
本节说明它落到哪里、以及还差什么。

### 7.1 期限怎么算

| 期限 | 落实在哪 | 判据 |
| --- | --- | --- |
| 关闭浏览器（最后标签页 + 5 分钟宽限） | `sessions` / `session_tabs` 两张表 + `CheckupManager._lease_end` | 最后一个标签页的离开时刻（或它最后一次续租）加 300 秒 |
| 该次体检之后的第三次新体检结束 | `CheckupManager.retention_of` + `store.later_terminal_instants` | 按 `rowid`（真实提交顺序）数到第 3 个进入终态的任务，取它的 `finished_at` |
| 历史数据（无会话归属） | `store.retention_baseline_at()` | 早于"这份库开始记录保留期"的时刻 |
| 已经清理过 | `tasks.details_cleared_at` 墓碑 | 具名回答"明细已被清理"，而不是"没有这个任务" |

两条期限**任一先到**：`RetentionView.expires_at` 报的是更早的那一个，`reason` 说的是
先到的那一个。到期时刻**不写进修订**：它随后来完成的体检变化，冻结进不可变修订就等于
把一个会变的答案写成常数。

重试与补查不新建 `tasks` 行，所以不计数——这一点有测试钉住（`test_checkup_sessions.py`）。

### 7.2 到期之后做什么，以及为什么是这个顺序

1. **复用立刻停止**：`KeyedCache` 只对**跨任务**读取问一句"来源还在期限内吗"。同任务读自己
   的条目永远允许——那是它自己的证据，拒绝它只会让一个正在到期的会话重新花钱买同一页。
2. **明细立刻拒绝提供**：`/result`、每个图层、设施路线一律 410 `checkup_details_expired`，
   并加 `Cache-Control: no-store`。**不做"少给一点明细"**：一张设施更少的图会被读成
   "这次只找到这些"，而真实答案是"这一部分不再被授权查看"。
3. **汇总另走一条路**：`/retained-result` 给出定稿时冻结的白名单汇总（结论、分数区间、
   面积、计数、停止原因）与到期原因。
4. **清理**：先落墓碑（两个巡检者只有一个能删）、再删整个任务目录（含**没有索引行**的
   修订文件）、最后丢掉进程内属于它的缓存条目。只删 `checkup_dir/tasks/<task_id>`。
5. **巡检**：由服务的启动钩子起一个 60 秒的循环。到期恰恰发生在**没有人看**的时候，
   只靠读取触发就等于"没人看就永远不清"。

### 7.3 汇总为什么是白名单

`retention.summary_of()` **逐项列出**允许留下的字段。黑名单式的"删掉这几个键"总有一天会
漏掉一项，而漏掉的那一项往往就是坐标。测试不是"字段对得上"，而是拿一份**真修订**的汇总
去断言：找不到任何设施标识、UID、名称、地址或成对坐标。

### 7.6 修正：删除之前先冻结汇总

`retention_manifest.apply` 现在对每条待清任务按顺序做：

1. 墓碑已存在 → 跳过；
2. 期限其实未到 → 跳过（清单是几分钟前算的）；
3. **这一版没有汇总、而修订文件还在** → 当场用 `retention.summary_of` 补写汇总
   （`store.set_summary`，`AND summary IS NULL`：只补空的，不覆盖已冻结的那一份）；
4. 文件已不在、且从来没有汇总 → 仍然落墓碑，但在结果里记为
   `no_revision_summary_available`，**说得出来**而不是悄悄少留一份；
5. 落墓碑 → 删目录 → 丢掉内存条目。

清单本身也提前说明：每条带 `summaryRecorded`，汇总数字里多一个 `totals.withoutSummary`。
"删完才发现结论跟着没了"这件事，现在在删之前就看得见。

### 7.7 v1 hybrid 运行残留：已清（另一个所有者）

`/api/v1/analysis/hybrid` 每跑一次就把 `plan/ledger/partial-result/diagnostics/failure/result`
写进 `hybrid_ledger_dir/<task_id>/`，而它**从来不删**：`HybridManager.prune()` 清的只是内存里的
job（1800 秒、或最近 20 个）。磁盘上的这些文件**只有一个写入点、没有任何读取点**——
`hybrid_ledger_dir` 在整个 `app/` 里只出现一次，就是拼出写入路径那一行；接口的读取全部走
内存里的 `jobs`。所以它们是纯诊断残留，删掉不影响任何服务。

`tools/hybrid_ledger_manifest.py` 的判据**不是另发明一套**，而是把 `prune()` 的口径搬到磁盘：
内存里还留着哪几次运行，磁盘上就留哪几次（`--keep-runs 20 --keep-seconds 1800` 即该函数的
两个常量）。默认只读；`--apply` 只删清单里逐条列出的**一级目录**，不是目录的条目只报告、绝不删。

**2026-10-09 执行**：

| | 前 | 后 |
| --- | --- | --- |
| `.hybrid-ledgers` | 108 MB | 28 MB |
| 运行目录 | 61 | 20 |
| 文件 | 227 | 68 |
| 清理的运行 | — | 41（83,613,895 字节，全部 `beyond_memory_prune`） |
| 额度账本 | 12,288 字节 | **一字未动** |

清单与执行结果：`evidence/hybrid-ledger-manifest-2026-10-09.json`、`evidence/hybrid-ledger-cleanup-2026-10-09.json`。
v1 hybrid 接口的 44 个用例在清理后照常通过。

**残留的一点**：`prune()` 仍然只清内存，所以这些文件还会继续长回来。判据现在有了工具，
但"定期跑一次"这件事还没有自动化 —— 这是它的接口所有者（v1 分析接口）该决定要不要加的事，
不是本次改动顺手替他决定的。

### 7.8 一处必须说明的副作用

`build_checkups()` 在应用对象构造时就会 `create_schema()`，所以**任何** `import app.main`
（包括我在验证期间跑的 `python -c "import app.main"`）都会对真实数据目录做一次**加列迁移**
并写入保留期基线与新建的表。这一步是幂等且只增不删的（新增 `sessions`、`session_tabs`、
`meta` 三张表、`tasks`/`revisions` 各两列、一行 `meta`），但它确实改动了部署数据目录。
本次核对过：**没有删除任何明细**，`retention-manifest-2026-10-09.json` 是只读生成的
（生成前后 sqlite 文件的 mtime 与大小逐字节一致）。
