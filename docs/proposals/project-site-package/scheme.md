# 15 分钟生活圈项目建设方案

> 用途：划定两个独立仓库的任务目标、边界、阶段交付和验收标准。
>
> 本方案不创建远程仓库，不替代现有后端或算法实现；它是拆分仓库和开展后续开发时的任务基线。

## 1. 总体目标

建立“项目发布站 + Demo/前端工作台”两个独立仓库，并通过 GitHub Actions 分别完成自动检查和静态发布：

1. 让访问者不依赖后端即可理解项目价值、功能、技术路线和结果边界；
2. 让访问者可以打开一个可复现的具体 Demo，完成一次从选点到报告的完整流程；
3. 为未来正式分析页保留明确导航，但不在生产条件未满足时开放真实 API；
4. 让介绍站和 Demo 可独立构建、发布、回滚，避免发布页被后端故障拖垮；
5. 保持现有项目的业务边界：15 分钟步行圈和 1 公里分类服务判断分别计算、分别解释。

## 2. 仓库划分

### 2.1 当前工程仓库：开发基线

当前 `Baidu-map` 仓库暂作为完整工程基线，保留：

- `backend/`：FastAPI 服务、地图接入、任务、设施和接口契约；
- `life-circle-algorithm/`：算法包、几何、实验和算法测试；
- `life-circle-demo/`：现有 React Demo 和正式分析工作台；
- 根目录需求、技术方案、当前状态和验收材料。

这个仓库不直接承担两个新公开仓库的职责，拆分时从这里抽取稳定的前端和文档内容。

### 2.2 仓库 A：项目发布站

建议名称：`Baidu-map-site` 或与最终产品名一致的站点仓库。

建议结构：

```text
site-repository/
├── index.html                 # 项目介绍首页
├── assets/                    # CSS、图标和静态图片
├── content/                   # 可选的版本和说明数据
├── README.md
└── .github/workflows/
    ├── ci.yml
    └── deploy-pages.yml
```

职责范围：

- 发布页首页；
- 产品能力、架构、可信度、路线图和限制说明；
- Demo 和正式页的外部导航；
- GitHub Releases、文档和源代码链接；
- GitHub Pages 自动构建和发布。

不包含：FastAPI 运行时、真实百度服务端密钥、OSM 图数据、长任务执行和真实分析结果伪造。

### 2.3 仓库 B：Demo 与前端工作台

建议名称：`Baidu-map-demo` 或与最终产品名一致的前端仓库。

建议结构：

```text
frontend-repository/
├── src/                       # 从 life-circle-demo 提取并整理
├── public/
├── tests/
├── package.json
├── README.md
└── .github/workflows/
    ├── ci.yml
    └── deploy-pages.yml
```

职责范围：

- 离线 Demo 页面；
- 可复用的地图、设施、统计和报告组件；
- 正式分析工作台前端；
- Demo 与正式模式的清晰配置切换；
- 前端测试和静态构建。

不包含：把后端密钥写入前端、在 Demo 失败时静默切换成模拟结果、把合成数据发布成真实社区结论。

## 3. 页面和导航目标

### 3.1 发布站页面

发布站至少包含以下内容：

| 页面/区域 | 目标 | 必须展示 |
| --- | --- | --- |
| 首页首屏 | 让首次访问者在 10 秒内理解项目 | 一句话介绍、核心价值、Demo 入口 |
| 产品能力 | 说明能做什么 | 15 分钟圈、设施、服务缺口、报告 |
| 方法与架构 | 说明如何实现 | React、FastAPI、百度、OSM、空间分析 |
| 可信度边界 | 防止误读 | Demo/真实、未知/缺失、15 分钟/1 公里 |
| 路线图 | 说明当前阶段 | 静态发布、离线 Demo、受控 API、正式开放 |
| 导航区 | 连接两个仓库的产物 | Demo 地址、正式页地址、GitHub 地址 |

### 3.2 Demo 页

Demo 默认使用离线数据，至少完成以下流程：

```text
选择演示点
  → 选择场景
  → 开始体检
  → 查看地图和 15 分钟范围
  → 筛选设施类别
  → 查看服务盲区/无法判断
  → 打开完整报告
```

必须保留的场景：

- 正常结果；
- 某类设施缺失；
- 数据不足；
- 分析失败和重试。

### 3.3 正式页导航

正式页面可以先是入口说明页，后续再替换为真实工作台。它至少要说明：

- 当前是否对公网开放；
- API 和地图服务位于哪里；
- 是否需要账号、调用预算和权限；
- 正式结果与 Demo 结果不会混用。

发布站与 Demo 的地址通过配置注入，不在业务组件中写死域名。推荐使用：

```text
PUBLIC_DEMO_URL=https://<demo-pages-url>/
PUBLIC_APP_URL=https://<official-app-url>/
PUBLIC_REPOSITORY_URL=https://github.com/<owner>/<repo>/
```

## 4. GitHub Actions 目标

### 4.1 发布站仓库工作流

文件：`.github/workflows/ci.yml`、`.github/workflows/deploy-pages.yml`。

CI 工作流：

1. 在 Pull Request 和 `main` 推送时触发；
2. 检查 Markdown、静态资源引用和 HTML 结构；
3. 检查外部链接配置是否完整；
4. 构建发布站静态产物。

部署工作流：

1. 在 `main` 推送或手动触发；
2. 使用 Node.js 或站点实际所需的最小构建环境；
3. 生成静态产物；
4. 使用 `actions/upload-pages-artifact` 上传；
5. 使用 `actions/deploy-pages` 发布到 GitHub Pages；
6. 只授予 `contents: read`、`pages: write` 和 `id-token: write` 等必要权限。

### 4.2 Demo 仓库工作流

CI 工作流：

1. 安装锁定依赖；
2. 运行 Vitest；
3. 运行 TypeScript 检查和 Vite 生产构建；
4. 在具备浏览器环境时运行 Playwright 离线验收；
5. 禁止 CI 默认访问真实百度接口。

部署工作流：

1. 使用 `VITE_ANALYSIS_MODE=demo` 构建可公开版本；
2. 设置与 Pages 项目路径兼容的 `base`；
3. 将 `dist/` 上传到独立 Pages 站点；
4. 不把服务端百度 AK 放进 `VITE_*` 变量；
5. 正式模式另行构建、另行部署，不覆盖 Demo 产物。

## 5. 分阶段任务目标

### 阶段 0：仓库准备

目标：确定两个新仓库的名称、所有者、可见性、Pages 地址和默认分支。

交付：

- 两个仓库建立并可由维护者访问；
- 仓库 README 标明与当前工程基线的关系；
- 确定 Demo、正式页和发布站的 URL；
- 确定是否使用自定义域名。

完成条件：外部链接、发布权限和维护责任没有未确认项。

### 阶段 1：发布站

目标：先让项目可以被介绍和理解，不依赖分析服务。

交付：

- 项目首页；
- 功能、架构、边界和路线图区块；
- Demo/正式页/GitHub 导航；
- 移动端布局；
- CI 和 Pages 部署工作流。

完成条件：断开后端仍能打开；构建成功；导航不会指向不存在的页面；所有模拟能力都有明确标识。

### 阶段 2：具体 Demo

目标：将当前已有 `life-circle-demo` 整理为可独立发布的前端仓库。

交付：

- 固定演示数据和四类演示场景；
- 地图、筛选、统计、列表、报告的一致数据流；
- Demo README、环境变量说明和启动命令；
- Vitest、Playwright 和生产构建检查；
- 独立 Pages 发布工作流。

完成条件：新用户无需 Python、百度 AK 或 API 服务即可完成完整演示；页面明确显示演示数据；桌面和移动宽度无关键操作遮挡。

### 阶段 3：正式页预留

目标：提供正式系统的导航和上线条件，不提前公开真实接口。

交付：

- 正式页入口或状态页；
- E8.2 与 Hybrid 的能力和边界说明；
- API 地址、鉴权、限流和数据状态说明；
- 正式模式独立构建配置。

完成条件：正式页不会误导用户认为 GitHub Pages 已经运行 FastAPI；Demo 和正式结果不会相互回退或混用。

### 阶段 4：正式服务接入

目标：在独立后端完成安全和真实样例验证后连接正式前端。

前置条件：

- FastAPI 部署在支持持续运行任务的环境；
- CORS 只允许正式前端域名；
- 服务端百度 AK 只存在后端运行环境；
- 用户/项目级鉴权、QPS 和调用预算已就绪；
- 任务和结果具备持久化或明确的重启策略；
- 完成真实社区样例和独立精度验证；
- 真实结果、部分结果、未知区域和失败状态均能解释。

## 6. 验收标准

### 6.1 发布站验收

- `main` 分支变更可自动构建；
- Pages 可访问首页；
- 首页不依赖 API、Python 或地图 AK；
- Demo 和正式入口清楚可见；
- 关键内容在手机宽度下可读；
- GitHub、文档和版本链接可用；
- 不出现服务端密钥、测试密钥或错误日志。

### 6.2 Demo 验收

- `npm ci` 后可执行 `npm test` 和 `npm run build`；
- 可从预设点完成一次完整演示；
- 正常、缺失、数据不足、失败重试四个场景均可复现；
- 地图、统计、列表和报告的类别数量一致；
- 服务盲区和无法判断不会混淆；
- 修改中心点后不会套用旧位置结论；
- 页面和报告持续标明为演示数据；
- 不访问真实百度服务即可通过离线验收。

### 6.3 正式页验收

- 页面明确当前开放状态；
- 正式 API 与 Demo API 不共用错误回退；
- 后端不可用时不静默显示合成结果；
- 生产配置中不存在服务端密钥泄露路径；
- 真实服务上线前的前置条件有可追踪记录。

## 7. 明确不在本次任务内的内容

- 不在 GitHub Pages 上运行 FastAPI 或 OSM 计算；
- 不把现有仓库全部代码无差别复制到两个新仓库；
- 不把 Demo 模拟结果改写成真实分析结果；
- 不在没有业务口径的情况下增加综合评分、人口覆盖率或自动选址；
- 不在没有账号、额度和限流策略的情况下公开百度接口；
- 不自动创建远程 GitHub 仓库、购买域名或修改 DNS；
- 不把 E8.3 离线实验描述为已上线生产能力。

## 8. 交付物清单

### 发布站仓库

- `index.html` 或站点源文件；
- 介绍内容和项目导航；
- 发布站 `README.md`；
- `.github/workflows/ci.yml`；
- `.github/workflows/deploy-pages.yml`；
- Pages 设置和环境变量说明。

### Demo 仓库

- React/Vite 前端源代码；
- Demo 数据、地图、报告和测试；
- `README.md` 与 `.env.example`；
- `.github/workflows/ci.yml`；
- `.github/workflows/deploy-pages.yml`；
- Demo 地址和正式页预留地址。

### 当前文件夹交付

- `outline.md`：项目介绍和对外叙事底稿；
- `scheme.md`：仓库划分、任务目标、阶段、工作流和验收方案。
