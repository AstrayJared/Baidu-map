# 15 分钟生活圈项目介绍总览

> 用途：作为项目发布页、README、路演材料和 Demo 入口页的统一内容底稿。
> 
> 内容依据：当前仓库的需求分析、技术实现方案、算法状态、后端说明和 `life-circle-demo` 前端。

## 1. 一句话介绍

15 分钟生活圈是一个面向社区和街道空间洞察的可视化工具：用户选择一个中心点，系统展示 15 分钟步行可达范围，统计范围内的民生设施，并按照独立的 1 公里规则识别分类服务缺口，最后生成带有数据来源和限制说明的体检结果。

它不是简单地在地图上画一个固定半径圆，而是尝试把步行路网、地图数据、设施分布、空间分析和结果证据放到同一个可解释的工作流中。

## 2. 项目要解决的问题

社区生活服务评估通常面临三个问题：

1. 直线距离不能代表真实步行体验，道路绕行、河流、障碍和通行关系会改变可达范围；
2. 设施数量和位置分散在地图数据中，难以快速判断哪些服务在生活圈内、哪些点位存在分类缺口；
3. 一个“覆盖良好”或“覆盖不足”的结论如果没有距离口径、数据来源和未知区域说明，很难复核，也容易被过度解读。

本项目的核心方向是先呈现可验证的空间证据，再给出有限范围内的辅助判断，不把单点分析包装成整个社区的综合评分。

## 3. 用户能完成什么

### 3.1 选择分析位置

- 使用预设的社区样例和中心点；
- 在地图上选点；
- 输入或调整经纬度；
- 在正式工作台中使用地点搜索、当前位置和百度坐标能力（取决于环境配置）。

### 3.2 查看 15 分钟生活圈

- 以中心点为起点计算或展示步行可达范围；
- 在地图上查看范围轮廓、已知可达区域和未知区域；
- 查看计算预算、停止原因、采样证据和结果质量；
- 明确结果是可用、部分结果还是证据不足。

### 3.3 查看民生设施

首期重点类别为：

- 菜市场；
- 药店；
- 小学。

用户可以按类别筛选设施，查看设施名称、位置、圈内状态及可用的来源或核验信息。

### 3.4 识别分类服务缺口

对明确的评估点位逐类判断其周边 1 公里内是否存在相应设施，并区分：

- 已发现该类设施；
- 当前数据足以判断但未发现该类设施；
- 数据不足，暂时无法判断。

“15 分钟内不可达”和“1 公里内没有某类设施”是两个独立问题，页面和报告不会用前者替代后者。

### 3.5 查看体检报告

报告围绕同一次分析生成，包含：

- 样例或中心点信息；
- 分析条件和规则口径；
- 生活圈结果及设施统计；
- 服务缺口和无法判断部分；
- 数据来源、结果质量、时间和限制说明。

## 4. 当前产品形态

当前仓库已经形成三种可运行入口：

| 模式 | 入口 | 用途 | 数据性质 |
| --- | --- | --- | --- |
| Demo | `VITE_ANALYSIS_MODE=demo` | 展示页面交互、地图、统计、报告和异常流程 | 固定模拟数据，明确标注演示 |
| 百度边界搜索 | `VITE_ANALYSIS_MODE=api` 或 `baidu` | 运行 E8.2 百度边界搜索工作台 | 依赖 FastAPI 和百度步行服务，结果可能部分或未知 |
| OSM + 百度 | `VITE_ANALYSIS_MODE=hybrid` | 运行 Hybrid v1.5 工作台 | 使用 OSM 路网辅助范围和百度步行验证 |

E8.3 POI 引导联合构圈仍属于离线实验，不是浏览器或生产入口。

## 5. 技术架构

```text
React + TypeScript + Vite
        │
        ├── Demo：固定场景、SVG 示意地图、统计、报告
        │
        └── 正式工作台：任务控制、地图、结果适配、设施与报告
                         │
                         ▼
                    FastAPI 后端
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       百度地图        OSM 数据       空间分析模块
          │              │              │
          └──────────────┴──────────────┘
                         │
                 任务状态与分析结果
```

### 5.1 前端

`life-circle-demo/` 使用 React、TypeScript、Vite、Ant Design 和 ECharts。主要职责包括：

- 管理中心点、分析状态、筛选条件和结果快照；
- 展示地图、设施、等时圈、盲区和未知状态；
- 将正式接口响应经过运行时校验和适配后再交给页面；
- 在 Demo 模式下使用统一的模拟服务，保证地图、统计、列表和报告读取同一份结果。

### 5.2 后端

`backend/` 使用 FastAPI 提供任务接口、参数校验、状态轮询、结果查询和取消能力，并负责百度调用、设施处理、证据保留和错误边界。

正式接口目前至少包含两套互相独立的契约：

- `/api/analyses`：百度边界搜索 E8.2；
- `/api/v1/analysis/hybrid`：OSM + 百度 Hybrid。

两套接口不共用请求体，不静默切换算法，结果中会保留相应的算法和数据来源标识。

### 5.3 算法与数据

- 百度边界搜索通过多个方向、局部扫描和边界细化获取 15 分钟圈证据；
- Hybrid 先使用 OSM 路网和辅助数据，再使用百度步行结果进行验证；
- OSM 水体等硬约束用于 Hybrid 的计算过程，地图展示使用明确的显示几何；
- 坐标转换、投影、距离单位和百度坐标体系由地理模块集中处理；
- 数据不完整时保留 `unknown`、`partial` 或 `degraded` 等状态，不将未知区域当作确定不可达。

## 6. 可信度与必须说明的边界

### 6.1 Demo 边界

Demo 使用固定模拟数据和示意地图，用于验证用户流程和信息层次，不验证真实社区精度。页面、报告和发布页都应写明“演示数据”。

### 6.2 正式结果边界

- 单个中心点的生活圈不能代表整个社区、街道或全体人口的覆盖率；
- 设施数量不等于设施容量、营业状态、服务质量或使用资格；
- 真实地图数据可能存在缺失、延迟、截断、权限和配额问题；
- 部分结果和未知区域必须保留，不能为了完整视觉效果静默填充；
- 真实计算完成不等于独立精度验收已经通过；
- 目前没有把未经定义的综合评分、自动选址或规划方案生成作为既定能力。

### 6.3 GitHub Pages 边界

GitHub Pages 适合托管项目介绍页和静态 Demo，不适合运行 Python、FastAPI、OSM 路网加载、长时间分析任务或服务端百度调用。真实分析服务必须部署在独立的后端环境中，并通过 HTTPS、CORS、鉴权、限流和预算控制对接前端。

## 7. 两个独立仓库的建议介绍方式

当前工程仓库可以继续作为开发和算法基线；面向展示时建议拆出两个独立仓库：

### 仓库一：项目发布站

职责：

- 项目首页和产品叙事；
- 能力、架构、数据边界和路线图；
- GitHub、文档、版本和 Demo 入口；
- 使用 GitHub Actions 构建并部署到 GitHub Pages。

它不应直接读取当前仓库的后端密钥，也不应依赖 FastAPI 才能打开首页。

### 仓库二：Demo 与前端工作台

职责：

- 从当前 `life-circle-demo/` 提取可独立构建的 React 前端；
- 默认发布离线 Demo；
- 预留或后续承载正式分析工作台；
- 通过独立的 GitHub Actions 执行测试和静态部署。

发布站只需要通过环境变量或配置文件指向仓库二的 Demo 地址和正式页面地址，两个仓库可以独立发布和回滚。

## 8. 对外介绍的推荐叙事

### 30 秒版本

这是一个把社区步行可达性和民生设施分布放到一张可解释地图上的工具。它同时回答“15 分钟能走到哪里”和“周边 1 公里缺什么”，并把数据不足和结果限制一起展示出来。

### 3 分钟版本

项目从一个中心点开始分析：前端负责交互、地图和报告，FastAPI 负责任务和数据编排，百度步行服务提供路线证据，OSM 和空间模块辅助范围构建。用户可以查看 15 分钟生活圈、菜市场/药店/小学分布和分类服务缺口。当前公开展示先使用可复现的离线 Demo，正式 API 需要独立部署、鉴权、限流和真实样例验收。

### 发布页必须出现的三句话

1. Demo 是可操作的模拟数据演示，不是真实社区结论；
2. 15 分钟步行圈与 1 公里分类服务判断是两套独立指标；
3. GitHub Pages 承载静态页面，正式分析服务需要独立后端。
