## 0. 结论

项目经历过两次目录整理：一次集中搬迁**在同一批改动里被撤回**，一次"先建索引、分批迁移"的方案**从未合入**。结果是仓库继承了两次整理的*产出*（根目录启动器、一个只装一份文档的 `docs/`），却没有继承任何一次的*规则*；两个独立仓库又被放在主仓库工作区内且未被忽略。

因此本方案不重做一次"大搬迁"，而是：

1. **先划边界、再建索引、最后分批迁移**（沿用未合入方案 `4c839bb6` 的策略，而不是被撤回的 `68c336c3`）。
2. **运行路径一律不动**：`backend/`、`life-circle-demo/`、`life-circle-algorithm/`、`data/`、三个启动器、契约生成目标在本次整理中保持原位。搬迁的每个路径都有代码级代价（见 §6）。
3. **两个独立仓库迁到与主项目同级**，各自保留 Git 历史、远端、CI 与 Pages 工作流；不采用 submodule/gitlink。

## 4. 分阶段方案

每一阶段是**一个提交**，只做搬移与链接修复，不夹带内容改写；因此每一阶段都可以单独 `git revert`。

   ```gitignore

   intro-page/
   # 根目录虚拟环境（backend/ 与 life-circle-algorithm/ 的已各自忽略）
   .venv/
   ```

   `Baidu-map/`（旧克隆）**不写进 `.gitignore`**：忽略一个 96 MB 的偶然副本等于把它永久留在工作区。它的处置见 Phase 4。

**验收**：两个子仓库各自的 CI 命令在本地通过 —— 站点 `npm ci && npm run check && npm run build`（Node 22），Demo `npm ci && npm test && npm run check && npm run build` 加上它自己的 Playwright 套件；`git -C <repo> rev-parse --show-toplevel` 指向新路径；主仓库 `git status` 干净。

## 6. 影响面（为什么不做"大搬迁"）

- **26 个文件**在 `backend/tools/` 与 `backend/tests/` 里用 `Path(__file__).parents[2] / 'life-circle-*'` 定位兄弟目录（实测 `grep -rl "parents\[2\]"`）。这些引用按相对层级写死，任何一层目录变动都会集体失效。
- **1 处文档链接写在代码里**：`backend/tools/report_hybrid_validation.py:151`。
- **契约生成器同时写两个仓库**：`export_contract.py` 的输出跨 `backend/` 与 `life-circle-demo/`，所以这两个顶层目录必须保持兄弟关系。
- **两个子仓库的耦合是 URL 级与源码级的，不是路径级的**：站点只通过 `PUBLIC_*` URL 指向主仓库；Demo 的 `src/` 是 `life-circle-demo/src` 的同步副本（目前有 72 个文件内容不一致，7 个文件只在主仓库、2 个只在 Demo）。迁出目录**不会**修好这份漂移，需要在 Demo 的 README 里写明同步范围与"不要整目录覆盖"的例外（该 README 已经列了 3 条例外）。

## 7. 回退

每个阶段都是"只搬移 + 只修链接"的单个提交：`git revert <commit>` 即可回到上一状态；Phase 3 因为跨仓库，回退是把它移回 `intro-page/` 并恢复 `.gitignore` 那一行。任何阶段都不应包含内容改写，因此不存在"回退后内容对不上"的情况。
