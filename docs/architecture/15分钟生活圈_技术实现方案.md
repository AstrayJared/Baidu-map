## 1. 文档定位与总体路线

### 1.1 文档目的

本文确定从前端 Demo 到正式系统的总体技术路线，覆盖技术栈、页面与模块职责、数据流、API 接入方向、开发顺序和验收要求。

本文是后续逐模块设计的依据，不展开接口字段、数据库表结构、算法参数及部署配置。下文描述的是计划实现的能力，不代表代码、算法或 API 接入已经完成。

已确认的实施方向：

- 使用 **React + Python** 作为主技术栈；
- 先完成可交互的前端 Demo，验证页面效果与完整操作流程；
- Demo 使用本地模拟数据和示意地图；
- 页面效果确认后，再开发后端、空间分析算法并接入百度地图能力；
- Demo 中的业务页面、图表和报告组件尽量沿用到正式版。

### 1.2 分阶段路线

| 阶段 | 目标 | 交付重点 |
| --- | --- | --- |
| 第一阶段：前端 Demo | 确认产品效果、信息层次和交互流程 | 可运行的前端、固定演示数据、正常与异常场景 |
| 第二阶段：真实功能接入 | 让演示流程产生有真实数据依据的结果 | 百度地图、Python 后端、设施数据、等时圈与盲区分析 |
| 第三阶段：验证与交付 | 验证真实社区结果并形成可复现交付 | 对比测试、异常处理、性能检查、运行文档和开源材料 |

### 1.3 必须延续的业务边界

1. **15 分钟生活圈**回答从中心点出发可以步行到达哪些区域和设施。
2. **1 公里服务盲区**回答被评估点位周边是否缺少菜市场、药店或小学。
3. 两套指标分别计算、分别解释，不能相互替代。
4. 单个中心点结果不代表全社区人口覆盖率，设施数量不代表服务容量或质量。
5. 数据不足与设施缺失分别呈现；无依据的评分、等级、自动选址及规划方案生成不纳入本次技术基线。

## 2. 技术栈与选择原则

### 2.1 技术栈

| 层次 | 技术选择 | 使用阶段与职责 |
| --- | --- | --- |
| 前端基础 | React、TypeScript、Vite | Demo 开始使用，正式版沿用；组织界面、类型检查和前端构建 |
| 界面组件 | Ant Design、CSS Modules | 表单、筛选、列表、抽屉、状态提示及页面样式 |
| 前端状态 | React Context、useReducer | 管理中心点、分析状态、类别筛选和当前结果 |
| 统计图表 | Apache ECharts | 分类设施数量、问题统计及报告图表 |

| 正式地图 | 百度地图 JSAPI 4.0 | 真实底图、选点、设施与分析结果图层 |

| 空间分析 | NumPy、Shapely；投影处理按需使用 pyproj | 采样数据处理、区域构建及空间关系判断 |
| 数据存储 | PostgreSQL、PostGIS | 正式阶段保存分析任务、结果及空间数据 |

React 官方提供使用 Vite 与 TypeScript 创建应用的路径。本产品先采用前端单页应用，界面与后端分析职责分开。[React 官方文档](https://react.dev/learn/build-a-react-app-from-scratch)

Ant Design 提供 React 界面组件，ECharts 提供统计图表能力；页面布局、颜色与图表口径保持统一。[Ant Design 文档](https://ant.design/docs/react/introduce/)、[ECharts 文档](https://echarts.apache.org/en/index.html)

FastAPI 支持基于类型的数据校验及自动接口文档，后续按模块逐步完善接口定义。[FastAPI 官方文档](https://fastapi.tiangolo.com/features/)

正式地图按当前官方文档选择百度地图 JSAPI 4.0；地图展示和分析数据获取分工明确。[百度地图 JSAPI 4.0 文档](https://lbs.baidu.com/docs/jsapi?title=jsapi4/index)

- 具体依赖版本在各阶段开始时核对兼容性，使用锁定文件记录可复现版本；本文不指定未经验证的版本组合。
- 队列、独立缓存服务和计算任务执行机制留到后端模块讨论，不作为 Demo 前置条件。
- 后续下载、依赖安装、缓存及较大运行数据默认安排在 D 盘；具体目录在实施时确认，本次不新增安装或调整环境。

## 3. 前端 Demo 实现方案

### 3.1 Demo 的目标与边界

Demo 用于验证用户能否理解两类分析结果，以及页面布局、地图联动、设施筛选和报告查看是否顺畅。它不验证算法精度，也不作为真实社区分析结果。

- 使用本地固定模拟数据，不调用真实地图 API、后端或空间分析算法。
- 页面、地图和报告持续显示“演示数据”标识。
- 采用预制的不规则区域展示等时圈示意；示意区域不声明为真实路网计算结果。
- 不把虚构设施、道路或坐标对应的模拟结果包装为真实社区结论。
- 首期围绕菜市场、药店、小学，展示分类数量、问题位置及数据质量说明。

### 3.2 页面布局

采用桌面浏览器优先的地图工作台，窄屏下侧栏收起，通过抽屉查看分析条件与结果。

| 区域 | 展示内容与交互 |
| --- | --- |
| 顶部 | 产品名称、当前样例、演示数据标识 |
| 分析面板 | 样例选择、中心点坐标、分析条件、开始体检 |
| 地图区域 | 中心点、模拟道路、分类设施、等时圈示意、灰色区域与图例 |
| 结果面板 | 圈内设施数量、分类盲区列表、无法判断部分 |
| 报告抽屉 | 当前分析条件、地图或结果摘要、统计图表、问题位置及结论限制 |

设施类别用一致的颜色与符号区分；灰色区域表示模拟的设施缺失，数据未知使用不同标识。等时圈图层与 1 公里盲区图层应可独立查看。

### 3.3 核心交互流程

**选择演示点 → 开始体检 → 查看地图与统计 → 筛选设施 → 定位盲区 → 查看报告 → 修改位置重新分析。**

- 支持从预设样例选择中心点，也支持地图选点和坐标输入。
- 预设演示点提供完整结果；其他位置显示“暂无演示数据”，不能套用预设结果。
- 点击设施可查看名称和类别；点击盲区列表项可定位相关问题点位或区域。
- 切换设施类别时，地图、列表和相关统计同步更新；报告的全量或分类范围应有明确标识。
- 修改中心点后，明确显示待重新分析状态；旧结果保留原中心点标识，不改写成新位置结果。
- 分析过程中显示加载状态，不用虚构的真实算法进度描述模拟等待。

### 3.4 固定演示场景

| 场景 | 模拟内容 | 预期表现 |
| --- | --- | --- |
| 正常结果 | 三类设施及完整分析结果 | 可以查看图层、统计、详情和报告 |
| 某类设施缺失 | 某些点位缺少菜市场、药店或小学中的一类 | 对应盲区、缺失类别和问题说明一致 |
| 数据不足 | 某类设施或部分区域信息无法判定 | 显示无法判断，保留其他有效结果，不按盲区处理 |
| 分析失败 | 本次分析无法完成 | 显示失败和重试入口，保留已选择的位置 |

地图、图表、列表和报告读取同一份场景结果，统计由场景中的设施与问题数据一致生成，避免分别维护数值。模拟数据保留固定标识，便于复现与测试。

需求尚未确认的距离口径、评估范围等，在 Demo 中作为“演示条件”说明；不将它们默认为正式业务规则，也不在 Demo 中实现距离计算。

### 3.5 前端组织与正式版复用

| 部分 | 负责内容 | 正式阶段处理 |
| --- | --- | --- |
| 页面组件 | 分析表单、统计卡片、设施列表、报告抽屉 | 沿用并根据真实数据修正 |
| 展示状态 | 当前选择、分析状态、筛选条件、结果版本 | 沿用，接入真实任务状态 |
| 数据服务 | 获取样例、发起分析、查询状态、获取结果 | 从模拟实现替换为后端请求实现 |
| 地图渲染 | 展示中心点、设施、区域并响应选择事件 | 将 SVG 渲染替换为百度地图实现 |

页面通过统一数据服务获取结果，不直接读取模拟文件。模拟服务以异步方式返回状态和结果，使页面能够提前覆盖等待、失败与重试。

SVG 地图与百度地图实现相同的业务展示职责，但不强求内部绘制代码复用。经纬度、SVG 示意位置及正式地图位置需要明确区分，不能混用。

数据对象提前划分为：**分析条件、任务状态、设施、等时圈、盲区、统计、数据质量说明**。本阶段仅统一对象含义，字段协议留到模块设计。

## 4. 正式系统技术方案

### 4.1 系统结构与数据流

采用模块化单体后端，空间分析逻辑与请求处理分开。

**React 前端 → FastAPI 分析服务 → 地图接入模块 / 空间分析模块 → 结果存储 → 地图、图表和报告展示。**

基本处理流程：

1. 前端提交中心点及已确认的分析条件。
2. 后端校验输入，创建分析任务并记录条件。
3. 地图接入模块获取所需设施及步行测时信息，设施处理模块进行分类、去重与完整性检查。
4. 等时圈分析与 1 公里盲区分析分别产生结果及限制说明。
5. 汇总分类统计与报告内容，保存任务状态、结果和必要来源信息。
6. 前端查询任务状态，加载同一次分析的地图、统计和报告。

浏览器负责底图加载、交互及结果渲染；设施检索、批量步行测时和分析编排统一由后端负责。对于较长分析，通过任务状态查询展示进度，避免页面持续等待一个无法解释状态的请求。

### 4.2 模块职责

| 模块 | 主要职责 | 主要输入与输出 |
| --- | --- | --- |
| 分析任务 | 创建分析、记录条件、管理执行状态 | 中心点与条件 → 任务标识、状态 |
| 地图接入 | 封装坐标处理、设施查询和步行测时 | 位置与查询范围 → 标准化设施、距离、时间 |
| 设施处理 | 分类、去重、保留来源与完整性信息 | 原始设施 → 分类设施集合 |
| 等时圈分析 | 根据真实步行测时推导近似可达区域 | 中心点、时间阈值、测时结果 → 等时圈与限制说明 |
| 盲区分析 | 按确认的 1 公里规则逐类判断 | 评估范围、设施、距离口径 → 问题点位及区域 |
| 统计与报告 | 汇总同一次分析结果 | 分析产物 → 分类统计、报告内容 |
| 数据存储 | 保存任务条件、状态、结果和必要的数据来源信息 | 分析过程 → 可追溯结果 |

### 4.3 接口能力概览

| 能力 | 主要输入 | 主要输出 |
| --- | --- | --- |
| 获取样例 | 样例选择条件（如有） | 样例名称、中心点及可用分析条件 |
| 创建分析 | 中心点、设施类别及确认后的评估条件 | 分析任务标识、初始状态 |
| 查询状态 | 分析任务标识 | 执行状态、已完成部分、失败或限制说明 |
| 获取结果 | 分析任务标识 | 等时圈、设施、盲区、统计、报告与数据质量说明 |

采用 HTTP API 连接前后端。具体请求路径、字段、状态枚举、错误码和大结果返回方式在模块讨论时确定。前端仅依赖统一后的业务结果，不直接依赖百度 API 的原始响应结构。

同一次分析的条件、结果和报告必须可关联。用户修改条件后创建的新分析，不能被较早请求返回的结果覆盖。

### 4.4 地图 API 接入方向

接入范围包括位置与坐标处理、设施检索、步行路径与批量测时。正式开发前先用一个真实样例验证坐标、查询完整性、调用权限及测时结果。

百度提供步行批量算路能力，可作为测时来源；实际账号是否可用、配额和批次限制在接入阶段验证，本文不假定调用额度。[步行批量算路文档](https://lbsyun.baidu.com/docs/webapi?title=routematrix/routchtout-walk)

地图接入模块统一负责：

- 将供应方响应整理为内部设施、距离、时间及错误信息；
- 分页或范围查询的完整性检查，标注被截断或未完成的数据；
- 超时、受控重试、调用频率控制与调用量记录；
- 按位置、分析条件和数据时效区分缓存结果。

### 4.5 空间分析方向

#### 等时圈分析

以中心点向周边点位的真实步行测时为基础，先验证采样与近似区域构建路线。正式结果保留不可达点、障碍和边界不确定性，避免简单连接点位而跨越河流或封闭区域。

采样密度、范围扩展、区域构建方法、允许误差与调用预算在算法模块单独讨论。路网真实可达关系以已获取的测时与路径证据为依据，不能承诺数据未反映的临时通行变化已被完整处理。

#### 设施统计

圈内展示与中心点步行可达判断保持一致，对近似边界附近的设施进行必要核验。服务盲区所需的圈外参考设施单独保留，不混入圈内设施数量。

#### 服务盲区分析

按确认后的距离口径和评估范围执行 1 公里分类判断，与等时圈模块分开。查询范围需要覆盖评估区域外的邻近设施，避免边缘点位因数据截断被误判。

区分有设施、设施缺失和无法判断。灰色区域应对应可核查的问题点位或区域依据，不把少量点位结论任意扩大为整片区域。

#### 坐标与空间单位

明确原始坐标、地图展示坐标和计算坐标，统一转换入口、经纬度顺序及距离单位。不能直接把经纬度差当作米，也不能将百度坐标直接标注为 WGS84。

Shapely 用于平面几何处理，本身不负责坐标转换；pyproj 用于适用的投影处理，不能默认承担百度坐标体系转换。使用前应确认数据坐标含义及转换链路。[Shapely 官方文档](https://shapely.readthedocs.io/en/stable/manual.html)

### 4.6 存储与结果一致性

正式阶段使用 PostgreSQL 保存任务与业务结果，使用 PostGIS 管理需要存储和查询的空间对象。[PostGIS 文档](https://www.postgis.net/documentation/getting_started/)

存储范围包括分析条件、任务状态、结果、数据来源与时间、必要的规则版本及限制说明。地图数据的可缓存范围和保留周期在接入阶段核对，不默认长期保存全部原始响应。

数据库表结构、空间字段、索引、迁移方式及结果保留周期留到存储模块讨论。任务结果存储用于状态查询与追溯，不自动增加用户可见的历史记录功能。

### 4.7 异常、运行与扩展

- 区分无设施、查询失败和数据不完整；部分失败时保留有效结果并说明限制。
- 正式运行失败时不自动回退为模拟结论；演示模式与真实模式明确区分。
- 服务端凭据保留在后端；浏览器地图配置按平台要求限制使用范围；代码、文档和日志不记录敏感凭据。
- 正式交付采用可复现的容器化运行方案，记录任务耗时、地图调用量、失败率及数据不足情况。
- 异步任务执行、进程重启后的任务恢复和重复请求处理在后端模块设计时确定；不在请求处理函数中混入不可管理的长计算。
- 队列、独立缓存服务及计算任务执行机制根据正式模块需求细化，不作为 Demo 前置依赖。

## 5. 开发顺序、验收与后续讨论

### 5.1 实施顺序与阶段出口

| 步骤 | 主要工作 | 完成标准 |
| --- | --- | --- |
| 前端 Demo | 页面、SVG 示意地图、模拟数据、完整交互 | 四种场景可演示，地图、统计与报告一致，页面效果完成评审 |
| 真实地图与数据 | 百度地图、后端地图接入、坐标校验、设施检索与分类 | 一个真实样例的位置和设施可核对，数据限制有说明 |
| 分析能力 | 后端任务、等时圈、1 公里盲区及结果存储 | 两套指标独立运行，结论附带依据 |
| 联调与交付 | 报告、异常、性能、真实对比及运行文档 | 需求文档中的业务验收用例得到验证，项目可复现运行 |

先确认 Demo 效果，再进入正式能力开发。真实地图与设施接入稳定后，再逐步替换模拟分析结果；接入过程中的混合数据页面必须标明仍使用演示结果的部分。

### 5.2 Demo 验收

| 检查项 | 通过条件 |
| --- | --- |
| 核心流程 | 从预设演示点开始，能够完成筛选、问题定位和报告查看 |
| 结果一致性 | 地图、列表、分类数量及报告来自同一份结果，无重复或漏计 |
| 修改位置 | 重新分析前旧结果归属明确；非预设位置提示暂无演示数据 |
| 数据不足 | 未知数据与设施缺失明确区分，不显示为已确认盲区 |
| 失败与重试 | 分析失败后保留输入，可以重试或切换场景 |
| 显示效果 | 桌面工作台信息清晰，窄屏下侧栏可收起，无关键操作遮挡 |
| 演示标识 | 页面及报告始终说明为模拟结果，不声称完成真实计算 |

使用 Vitest 检查状态转换、分类筛选及统计一致性，使用 Playwright 检查完整操作流程与关键显示状态。[Vitest 文档](https://vitest.dev/guide/)、[Playwright 文档](https://playwright.dev/docs/intro)

### 5.3 正式版测试重点

正式版以需求文档第 13 节 AC-01 至 AC-12 为业务验收基线，重点覆盖：
