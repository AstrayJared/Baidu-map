## 1. 已确认的目标、范围与修订结论

### 1.1 首版交付范围

1. 保留百度 E8.2 与 OSM＋百度 Hybrid 两套成圈算法，算法接口和结果来源明确，不静默切换。
2. 两套算法均接入统一的设施检索、空间评估、灰区、评分和报告流水线。
3. 成圈阈值固定为 15 分钟；设施服务标准沿用步行距离 1000 米及现有误差带，不在本期改为 900 秒服务标准。
4. 两套成圈算法允许共用 OSM 设施评估路网，分别展示成圈引擎和覆盖模型来源。
5. 完整面积体检首先覆盖现有上海路网数据范围。其他地区保留百度成圈、设施检索、采样点证据和密度热力；没有空间支持时，面积和评分显示未知。
6. 首版完成购物、医疗、教育三大类。医院药房单列，未经确认不计入公共服务覆盖。公园文体、养老及社区公共服务留待后续版本。
7. 灰区表示“当前检索目录和模型下的疑似服务不足”，评分优先显示固定评估面积上的覆盖区间。
8. 热力图必须真实绘制在百度地图上，使用真实业务数据，并随地图平移、缩放正确更新。

## 2. 业务口径与默认规则

### 2.1 三种独立指标

- **圈内设施数量**：POI 原始地理点被算法计算圈面包含，使用 `covers` 包含边界点。显示“检索到的圈内设施”，不宣称是全量目录。
- **中心到设施可达性**：中心到设施入口的步行路线是否满足 900 秒，保留现有严格 POI 核验证据，与圈内几何命中分开。
- **圈内服务覆盖**：报告评估域内各位置到该类任意设施的步行距离是否满足 1000 米规则。这需要独立服务场，不能使用中心到设施的路线替代。

计数使用 POI 原始位置；导航和入口坐标不覆盖原始位置。坐标归一化、几何判断、路线核验的精度与来源分别记录。

### 2.2 固定距离规则

规则版本为 `walk-distance-1000-v1`，复用现有 `distance_within()` 的语义：

| 步行距离 d | 路线级判定 |
| --- | --- |
| `d < 900 m` | 满足服务条件 |
| `900 ≤ d ≤ 1100 m`，但 `d ≠ 1000 m` | 阈值附近，未知 |
| `d = 1000 m` | 按现有包含边界规则满足条件 |
| `d > 1100 m` | 该路线不满足条件 |
| 距离缺失、非有限数、错误指标或路线失败 | 未知 |

恰好 1000 米的特殊行为来自当前实现，本期保留，并在规则说明中展示。禁止先四舍五入再判定；100 米误差带不是把半径扩大为 1100 米。单条路线不满足条件不等于该位置没有其他可用设施或路线。

这些阈值是本项目业务规则，不宣称为国家规划达标标准。本期不新增面向普通用户的阈值、误差带和网格调参选项。

### 2.3 类别与公共服务来源

| 大类 | 计入公共覆盖的小类 | 单列或排除规则 |
| --- | --- | --- |
| 购物 | 菜市场、超市 | 门口及附属办公室不重复计数；疑似重复门店进入核查 |
| 医疗 | 普通药店 | 医院药房单列，未经确认不计公共覆盖；制药公司、仓库、兽药店排除 |
| 教育 | 小学 | 培训机构、幼儿园排除；地理可达不代表入学资格与学位供应 |

新接口统一使用 `primary_school`，旧 `school` 由兼容适配器转换。设施是否营业及是否开放属于独立证据：字段缺失不能视为已确认开放；明确停业或关闭的记录不参与服务覆盖。

服务评估默认允许圈外邻近设施服务圈内位置，地图在选中其服务路线时标注“圈外服务来源”；圈外设施不计入圈内数量，也不混入圈内密度热力。路径允许绕到圈外，不能先沿生活圈边界切断路网。

## 3. 接口、任务编排与不可变结果

### 3.1 两个引擎适配器

注册显式引擎 `baidu_e82`、`osm_hybrid`，内部提供统一能力：

```python
class IsochroneEngine(Protocol):
    engine_id: str
    async def compute(self, request, context) -> IsochroneSnapshot: ...
    def capabilities(self) -> EngineCapabilities: ...
```

`context` 提供任务 ID、取消令牌、截止时间、阶段回调及统一配额入口。预算和配置按引擎校验，不支持的引擎或档位返回 422，不自动回退到另一算法。

新编排必须直接调用成圈核心或 compute-only 适配器。旧 E8.2 管理器已在成圈后调用设施分析，不能复用该全流程后再检索一遍。旧 HTTP 接口继续兼容，后端公共传输仍统一走配额入口。

### 3.2 完整体检入口

新工作台使用 `/api/v2/checkups`。普通输入只包含中心、坐标系、引擎、成圈预算、类别和设施预算；阈值、网格策略、配额上限及服务地址均由服务端控制。

```json
{
  "schemaVersion": "checkup-v1",
  "clientRequestId": "client-generated-unique-id",
  "engine": "baidu_e82",
  "center": {"lng": 121.513925, "lat": 31.313079},
  "coordinateSystem": "bd09ll",
  "isochrone": {"budget": 400},
  "facilities": {
    "categories": ["shopping", "medical", "education"],
    "maxPoiRequests": 60,
    "maxRouteRequests": 120
  }
}
```

这是拟新增契约，不能发往现有两个接口。省略设施预算时使用上述标准值，允许降低，不允许超过首版上限；不允许通过请求覆盖 QPS。服务端响应返回实际采用的完整规则和模型版本。

| 接口 | 明确行为 |
| --- | --- |
| `POST /api/v2/checkups` | 202 创建或返回幂等任务；同请求 ID 不同参数返回 409 |
| `GET /api/v2/checkups/by-request/{requestId}` | 恢复创建响应丢失的任务 |
| `GET /api/v2/checkups/{id}` | 阶段、实际消耗、最新可用修订和取消状态 |
| `GET /api/v2/checkups/{id}/result` | 最新不可变报告快照；尚无快照时返回明确的未就绪状态 |
| `GET /api/v2/checkups/{id}/layers/{layerId}?revision=…` | 对应修订的图层数据、结果哈希及 ETag |
| `POST /api/v2/checkups/{id}/cancel` | 停止后续请求，保留已经发布的阶段结果 |
| `POST /api/v2/checkups/{id}/routes/{facilityId}` | 只查询该任务设施集合内的路线详情 |
| `GET /api/v2/capabilities` | 引擎预算档位、规则、数据版本和覆盖范围 |

任务状态使用 `queued / running / cancelling / completed / failed / cancelled`；业务状态另用 `complete / partial / insufficient`。阶段固定为 `isochrone / poi / accessibility / verification / reporting / ready`。`completed` 不代表目录齐全或算法精度达标。

### 3.3 快照和修订

每个已完成阶段发布递增的 `revision`，已发布内容不可原地改写。每份快照至少包括：

| 字段组 | 内容 |
| --- | --- |
| 身份 | taskId、revision、生成时间、中心和坐标系 |
| 成圈 | engineId、版本、参数、计算圈面、展示圈面、原质量和未知字段 |
| 范围 | 报告评估域、排除面积、模型支持域、投影及数据覆盖范围 |
| 设施 | POI 快照、分类及入口证据、查询覆盖和目录状态 |
| 分析 | 覆盖模型版本、三态网格、灰区、区间分和报告聚合 |
| 追溯 | 数据版本、规则版本、isochroneHash、resultHash、各预算消耗 |

`isochroneHash` 只标识圈面；`resultHash` 覆盖圈面、POI、规则和空间分析，不能直接复用 Hybrid 当前只针对成圈结果生成的哈希。

成圈阶段完成即显示圈面。设施失败、取消或超时不丢弃已发布圈面。点击设施路线产生独立详情证据，不自动改变已发布评分；重新评估须生成新修订。前端用任务 ID、引擎和修订隔离迟到响应。

### 3.4 存储、恢复和缓存

首版使用 SQLite 保存任务元数据与配额账本，以原子文件保存不可变空间结果。保持单服务进程，不引入 Redis 和分布式队列。CPU 几何及图计算放入受限后台执行器，不能阻塞 FastAPI 事件循环；共享图只读。

服务重启后将未完成任务记录为中断并保留阶段结果，不自动恢复付费请求。相同幂等 ID 返回原任务，用户主动重新计算使用新 ID。

缓存分为成功请求页、设施集合快照、路线和空间计算结果。成功页可以来自部分集合；它们可作为正向设施记录复用，但不能把集合补标为完整。失败响应不缓存为零结果。

缓存键包括坐标系、查询范围与参数、提供商和版本；空间结果额外包括算法、规则、网格、POI 和路网版本；路线键包括方向、UID、目标入口、路由指标及证据策略。采用 single-flight 合并相同在途查询。

跨任务缓存有效期按部署的数据使用约定显式配置，未配置时仅任务内复用，不默认永久保存或永久视为新鲜。报告使用原始数据时间，不因缓存命中而刷新采集时间。

## 4. 设施检索、分类和数据质量

### 4.1 查询范围

查询域为计算圈面在米制坐标下外扩 1300 米的范围。该值覆盖当前 1100 米误差带及入口偏移、近似坐标转换的工程余量，不是现实目录完备性证明。

查询范围不沿行政区名推断；圈面跨块、跨区时保留全部必要查询块。模型路由可经过圈外道路，但不得把超出已知路网覆盖的路径当作可靠结果。每格是否可判灰区，需要独立检查它周边必要查询范围和图覆盖是否充分。

### 4.2 自适应查询规划

现有固定 4×4、六关键词计划首轮即需 96 次请求，不能直接用于标准 60 次在线预算。新在线 planner 固定如下：

1. 以查询域包络的 2×2 粗块开始，只保留与查询域相交的块；以外接圆发起已有 around 检索，随后精确裁剪。
2. 各类别首轮轮转执行，再安排翻页，避免先耗尽某一类别预算。
3. 使用 `coord_type=3`、`radius_limit=true`、`scope=2`、`page_size=20`，页码从 0 开始。
4. `total=150`、重复 UID 分页、重复整页、总数变动或异常空页均保留不完整证据；对仍有价值的块细分。
5. 最细查询块边长为 250 米；每序列最多 8 页。分页、细分和重试共同受任务预算控制。
6. 预算耗尽、最细块仍饱和或查询失败时输出 partial，保留已获得设施，不能声称完成全量检索。

queryCoverage 记录每个块、类别、关键词、页码的请求与成功状态、总数、截断、失败和来源。每个已成功的响应独立计费和缓存；新增关键词不允许隐式突破 60 次预算。

百度官方说明单页最多 20 条，total 存在 150 上限；关键词检索执行完不等于现实目录齐全。[Place 3.0 文档](https://lbs.baidu.com/docs/webapi?title=placev3%2Fguide%2Fwebservice-placeapiV3%2FinterfaceDocumentV3)

### 4.3 统一分类和实体

后端词典是唯一权威，前端从类别定义生成显示映射。管线为：字段规范化 → 分类/异常隔离 → 来源 UID 合并 → 冲突处理 → 圈内判断。

同 UID 的分类或坐标冲突保留诊断，未解决记录不作为可靠覆盖来源。不同 UID 的近距离同名点只标为疑似重复，不能一律按 20 米合并门店。门口不作独立设施计数，但可在有明确关联证据时作为父设施入口。

原始 POI 坐标、导航候选坐标、确认入口分别保存。官方 navi_location 是导航引导点，可能是上车点，不等同于已确认步行入口。当前 Provider 白名单还需为新增业务证据扩展字段，不能在归一化时把未返回字段补成确定状态。

原命令行 POI runtime 具有配置哈希、执行窗口和账本门禁。提取其纯分类、规划、分页能力，为在线任务建立独立生产 runtime；不要伪造实验审批字段或绕过发送前记账。

### 4.4 两条数据质量轴

- `queryCoverage`：计划内查询和空间范围是否完成。
- `catalogCompleteness`：现实目录是否独立核实；百度关键词检索默认 unverified。

完成查询但未找到设施时，可形成条件性的模型缺口；查询失败或范围缺失时，不能由零结果推断缺口。即使目录不完整，可靠路线仍可证明一个具体位置存在已知服务。所有报告同时保留模型前提和检索状态。

## 5. 服务路网与覆盖计算

### 5.1 空间范围分层

1. **原始计算圈面**：用于圈内设施数量，保留成圈算法本身结果。
2. **报告评估域 A**：计算圈面扣除已有证据支持的不可评估水面，保留合法桥梁通道；排除面积单列。
3. **模型支持域**：具备路网覆盖、可解释接入和所需查询证据的区域；评估域中其余区域保留未知，不从分母消失。

E8.2 在缺少未知几何时可能用整个计算域作为 unknownRegion，不能机械相减，也不能从圈面存在推断内部全部实测。Hybrid 的 displayGeometry 是展示外壳，只用于外轮廓，不参与计数、评估范围和热力裁剪。

缺少水体或障碍资料时保持对应数据质量标记，不能声称完成可靠障碍扣除。空几何表示有结果且为空，null 表示无法确定；A 为零或不可确定时面积比例和分数均返回 null。

### 5.2 独立服务分析图

现有上海图元数据约为 27 万节点、72 万条有向边，主要障碍层为水体与桥梁；节点 barrier 的存在不代表路由已经执行门禁限制。新增独立的服务图版本，不改变 E8.2、Hybrid 或 OSM 离线基线的既有语义。

从已有 PBF 补充围墙、栅栏、门、步行权限、条件通行属性及层级。明确禁止的边或节点不可通过；未知门禁保留歧义，不假定开放或关闭。桥隧只按真实拓扑连接，平面坐标交叉不创建路口。

服务图有两个只读视图：

- 明确允许图：只使用明确可用的连接。
- 可能允许图：额外包含条件不明但可能通行的连接，仍排除明确禁止的通路。

明确允许图已有满足条件的路径，可形成模型覆盖；可能允许图也超过服务范围，才可进入疑似缺口判断；两图结论不同为未知。不得因全部关闭未知门禁而制造灰区。

图按进程加载一次。用图视图与任务局部虚拟节点表示入口，不为每格或每类别深复制整座城市图。准备结果记录 PBF 哈希、图构建版本、规则版本和覆盖范围；缺少新增侧车数据时降低模型可用性，不冒充完整功能。

### 5.3 入口接入

POI 原始点和导航点只是入口候选。正常模型接入要求距离不超过 50 米、连接段不穿过已知水体或围墙，并与实际道路层级和方向一致。

超过 50 米、多个不相容道路候选、门禁不明或跨障碍的接入进入未知及重点核验队列。沿用旧图最大 200 米吸附配置不代表新服务模型可将 200 米连接直接视为可靠。

未解决入口可能影响附近缺口判断，必须记录其影响范围，不能简单删除该设施后判灰区。明确停业、排除类别等记录则按其确定规则排除。

### 5.4 反向多源最短路

对类别 c 的设施入口集合 F，计算每个位置 x 到任意设施的最短模型距离：

`d_c(x) = min(route_distance(x → f)), f ∈ F_c`

实施固定为：

1. 在设施所在道路中部建立虚拟节点和分段边，保留物理道路正反向关系。
2. 在反向有向图上，以该类别全部有效设施入口为源，运行截止 1100 米的多源 Dijkstra。
3. 将评估点合法接入成本和设施入口连接成本计入总距离。
4. 沿方向恢复部分可达边区间，处理同边起终点直接路径，不绕到无必要的端点。
5. 在明确允许图和可能允许图上分别计算，用于形成覆盖、缺口或未知结论。

现有 cutoff_dijkstra 权重写死为 travel_time_s，边区间恢复也使用该权重；两处必须同时参数化为距离，不能只改搜索函数。原图的 source seeds 不能直接用于反向图，入口方向和分段成本需重新构造。

截止范围未发现路线不自动等于缺口：还需确认必要数据范围、设施查询和入口问题已处理。路径可绕出生活圈，不能为便于计算把路网裁到圈内。图覆盖边界造成的缺路归入未知。

### 5.5 坐标与几何

地图和百度接口使用 BD09LL，OSM 源数据为 WGS84；面积、长度、缓冲、吸附和网格在米制坐标中运算。上海使用已有 EPSG:32651，两套圈面转换到相同评估投影后再进行设施分析。

复用集中坐标转换模块，保留其近似转换性质，不宣称测绘级精度。标准 GeoJSON 导出需要转换为 WGS84，不能把带 BD09 坐标的业务几何冒充标准 WGS84 GeoJSON。

数据范围外的百度入口仍可工作，但不加载上海路网去推断其他城市服务面积。模型服务范围依据有效覆盖几何和所需查询域判断，不仅检查中心是否位于上海。

## 6. 网格、百度核验和灰区

### 6.1 网格策略

使用投影坐标全局对齐的 50 米网格，两套算法共用网格原点。每格与报告评估域相交，各连通分量独立评估，不能用一个跨河格子的单个中心代表两岸。

支持点使用内部 representative_point 和具有合法接入的边界支持点。以下情况细分到 25 米：圈边界或障碍相交、内部状态不一致、距离落在误差带、模型与百度证据冲突。

25 米分量仍有冲突、无法接入或缺少评估支持时标为 unknown。叶格最多 5000 个；达到上限后不继续细化，未能形成一致结论的待细化格仍为 unknown，不通过静默粗化取得确定结果。

面积输出始终是带分辨率的模型估计。代表点有服务不能被表述为整格已实测；真实核验点数和模型面积分开报告。

### 6.2 格子三态

| 状态 | 必要条件 |
| --- | --- |
| covered | 明确允许的模型路径满足距离规则，入口与空间支持可解释 |
| gap | 必要查询完成，无影响判断的入口未决项；包含可能连接的模型仍不满足服务范围 |
| unknown | 其余情况，包括误差带、查询或图范围不足、入口歧义、冲突和细化不足 |

每格保存状态、最近已知设施、模型距离、入口接入、查询支持、图版本及证据等级。目录未独立验证时，gap 只能显示为疑似服务不足。

### 6.3 百度重点核验

标准设施核验预算为 120 次详细路线尝试，包含重试，按类别轮转，优先处理边界冲突、未知门禁、入口偏移和疑似灰区。直线距离仅用于候选排序和保守筛选，不能替代步行距离。

保留原有严格 poiEvidence 语义。当前严格映射要求路线端点与原目标几乎完全重合，不能把它全局放宽到成圈算法所用的 50 米偏移阈值。

新增证据分层：

- 原始 POI 的严格核验，继续使用现有字段。
- 返回道路端点之间的路线证据，保存实际起终点及偏移。
- 包含额外模型连接段的估计成本，单独标为模型值。

连接段未确认时，不得将道路端点路线提升为原始 POI 严格核验。单点结果不能覆盖整格；模型与核验冲突标为待细化或未知，不通过平均距离消除冲突。

“直线最近的前几家都失败”不能证明盲区。没有可解释候选排除依据时保留未知。百度返回一条超距路线，只能说明该返回路线超距，不能证明所有路径都不满足条件。

### 6.4 没有 OSM 的降级

保留百度圈面、真实 POI、密度热力和有限采样点路线证据。采样点按空间均衡选择并在类别间公平分配预算；不把普通二维插值用于生成面积灰区，不补造 25 米服务场。

该场景的面积服务覆盖和区间分在缺少空间支持时显示无法确定。成圈引擎不会因此自动变更，报告明确 coverageMethod 与不可用原因。

### 6.5 灰区合并及解释

每类 gap 格按共享边邻接形成连通分量，障碍两侧、仅点接触的分量不合并。几何并集后再次裁剪到报告评估域，保留孔洞、分量和原格 ID。

综合灰区固定为“三大类至少两类为 gap”。unknown 不计为缺失。面积按并集计算，不相加重复计数。

小于 2500 m² 的区域不默认显示标签，但几何和面积仍保留。显示简化不得改变统计几何，不使用闭运算抹掉河流、通道或孔洞。

每区返回 ID、不足类别、面积、证据等级、最近已知设施、查询状态、原因、建议和格子映射。建议由模板生成，指向补采、通道核查或设施核查，不将模型结果写成确定的建设选址结论。

## 7. 覆盖区间、评分和报告

### 7.1 固定分母

报告评估域面积记为 A。每类别覆盖、缺口、未知面积分别为 C、G、U，必须互斥且满足：

`C + G + U = A`

对应指标：

```text
覆盖下界 = 100 × C / A
覆盖上界 = 100 × (C + U) / A
可评估率 = 100 × (C + G) / A
```

所有面积指标以同一份冻结评估域为分母。不能通过删除未评估格来提高分数，也不能把有检索结果的部分面积当作整个社区。

三大类各占 1/3，分别加权下界和上界形成总体模型覆盖分区间。仅当三类没有未知面积时，区间自然退化为一个模型分；不显示人为取中点的单一总分。仅分析部分大类时显示类别区间，不将其改名为完整三类总分。

例：A=100，C=50，G=0，U=50，则覆盖分为 50—100，可评估率为 50%；不能显示 100 分。

这些区间以当前目录和路网模型为前提，不是统计置信区间，也不包含所有现实遗漏误差。没有人口数据时不输出人口覆盖率；设施数量不是容量、服务质量或政策准入。

### 7.2 报告内容

| 区块 | 内容 |
| --- | --- |
| 条件与范围 | 中心、时间、成圈算法、设施模型、距离规则、圈面积、评估域和排除面积 |
| 总览 | 三类总体覆盖分区间、各类可评估率、主要疑似缺口 |
| 设施结构 | 圈内检索数量柱状图，严格核验数独立显示 |
| 类别覆盖 | 三维雷达图展示有支持的类别值；未知轴留空；旁边区间条表达上下界 |
| 空间诊断 | 真实热力、灰区编号、面积、类别与定位入口 |
| 证据质量 | 模型面积、百度核验点数、查询缺口、入口问题、图覆盖及数据日期 |
| 建议 | 按证据生成补采、现场核查、通道核查或设施配置参考 |

雷达图不为凑维度虚构公园、养老等类别，不把未知补零。图表与地图读取同一 resultHash 和 revision；地图类别筛选不悄悄改变完整报告。

报告文案先采用确定性模板，不依赖额外语言模型服务。保留可打印布局；地图截图不可用时清楚标注，不能输出空白地图并声称完整导出。

## 8. 真正绘制在百度地图上的热力图

### 8.1 本期技术路线固定为自定义 Canvas

BMapGL 自定义 Overlay 的 initialize/draw、getPanes 和 pointToOverlayPixel 支持地图关联画布。本期采用自有 Canvas 以控制孔洞、未知域和多分量裁剪，不在实现时再选择 MapVGL，也不依赖未经验证的 mask API。[BMapGL 类参考](https://mapopen-pub-jsapi.bj.bcebos.com/jsapi/reference/jsapi_webgl_1_0.html)

两种互斥模式：

- **设施密度**：真实、去重后的圈内 POI 等权参与，米制核半径固定 120 米。圈外服务来源不混入此层；显示的是检索分布密度，不能直接用低密度判盲区。
- **服务覆盖**：直接使用后端格子三态。综合模式仅对三类均已知的格子按覆盖类别比例着色；其余格子显示未知纹理。单类模式显示该类覆盖与缺口，未知保持独立。

服务覆盖层不采用点核叠加，否则相同区域增加采样点就会变亮。服务色标固定 0—100，密度色标与单位独立显示；算法比较使用相同参数和色标，缩放不改变地理核半径。

### 8.2 覆盖物实现步骤

1. initialize 创建 pointer-events:none 的 Canvas，挂入公开的覆盖物容器，将热力置于设施与中心交互层之下。
2. draw 计算画布在覆盖物像素坐标中的原点，POI、网格和所有裁剪环使用同一个转换函数。
3. 按 devicePixelRatio 设置绘图尺寸，颜色缓冲可降采样，坐标和交互维持正常屏幕精度。
4. 每个 Polygon 将外环、内孔共同构成 Path2D，以 evenodd 裁剪；各分量独立，不制造跨分量连接。
5. 密度先在离屏缓冲计算，再查色带；服务覆盖按原始格值绘制，不跨障碍或未知区域插值。
6. 最终 alpha mask 同时限制计算圈面和有效支持条件，热力核扩散不得越界或填孔。
7. 用 requestAnimationFrame 合并视角变化和数据更新，监听真实移动、缩放结束、resize 等 SDK 事件。
8. 首版地图固定二维俯视、北向上，不依赖未验证的旋转、倾斜投影效果。
9. 通过地图事件及空间索引拾取格子，Canvas 不抢占拖动和滚轮。
10. 卸载时移除覆盖物、监听、观察器、worker 和动画任务，兼容 React StrictMode。

设施密度没有 POI 时不生成随机热力点。真实 POI 存在但查询不完整时可以显示热力，同时显示数据范围提示。

### 8.3 地图状态和交互

将地图拆为稳定 MapHost 和独立圈面、设施、热力、灰区、路线、中心图层。各层持有自身覆盖物引用，增量更新；日常切换不执行 clearOverlays，不重建整个地图。

panTo/fitView 仅用于首次结果、新中心确认或用户点击定位结果。图层开关、筛选和详情不会把拖动后的地图拉回。Marker 点击不冒泡成地图选点。

设施超过 100 条使用聚合或可见视口绘制，完整数据仍参与热力和统计，不能静默截断。最多 5000 个格使用单 Canvas，避免每格创建一个 React 组件或百度 Polygon。

沿用 LocationControls、现有布局和双算法会话缓存。待分析中心、结果中心分别标注；更改坐标或拖动中心标记只更新待分析条件，点击开始后才发起新任务。失败保留上一份有效报告并注明条件。

图例分别展示：服务不足灰色、数据未知淡紫或斜线、算法边界不确定黄色虚线。问题卡片定位已有灰区，不自动开始新分析。窄屏使用抽屉和折叠条件面板，保证地图可用面积。

### 9.2 全路径统一调度

两个成圈算法、设施核验和点击详情共用路线闸门；POI 查询共用地点闸门。相同账户/应用真实共用的配额池不能仅按 AK 字符串各自隔离。

采用原有响应完成后间隔，并保留高精度计时、提前唤醒复查、冷却和取消检查。每次网络尝试都在同一调度点检查服务上限、阶段预算、每日应用预算和截止时间，发送前事务预留。失败重试、已发送但状态不明的尝试均计入消耗，不能在进程重启后清零。

日界限使用 Asia/Shanghai 的部署配置。浏览器 SDK 定位搜索及其他应用不在后端账本中，因此界面称“本应用预算余额”，不能声称是百度账号实际剩余额度。20% 余量不能保证外部应用大量调用时仍不触发上游限制。

响应后间隔模式吞吐近似 `1 / (响应耗时 + 间隔)`，16/8 只是上限，不是实际吞吐承诺。并发提速需要单独的发送/响应时序和真实限流验收，不纳入本期完成条件。

### 9.3 每任务预算

| 预算池 | 标准值 | 计数规则 |
| --- | --- | --- |
| 成圈 | B，默认 400 | 沿用引擎支持档位，实际尝试包含重试 |
| POI | 60 次 | HTTP 尝试，包含分页、细分和重试 |
| 设施核验 | 120 次 | 详细路线尝试，包含重试 |
| 点击详情 | 最多 20 次 | 同一任务独立上限，缓存命中不计新请求 |

任务完整上限为 **B＋140 次路线尝试、60 次地点检索尝试**，界面分池显示，不只显示“预算 400”。标准体检本身为 B＋120，20 次用于后续详情交互。

60 次 POI 不保证冷启动查询完整；预算不足发布部分目录，并保留相应未知面积。1600 次应用日预算最多支持 26 个满 60 次检索任务；降档后 80 次只够一个此类任务再留少量余量。缓存与自适应规划因此是必要能力，不保证每天任意数量的全新区域体检。

官方矩阵按起终点路线对数计算配额及并发，不能按 HTTP 请求数计算；该判断保留为后续接入约束，本期不启用矩阵。[百度矩阵说明](https://lbsyun.baidu.com/docs/webapi?title=routematrix%2Froutchtout)

## 11. 实施顺序与验收标准

### 11.1 六阶段交付

| 阶段 | 必须交付的结果 | 进入下一阶段的条件 |
| --- | --- | --- |
| M1 接口与快照 | 双引擎适配、v2 任务、不可变修订、旧接口兼容 | 无重复设施请求，幂等、取消和旧契约测试通过 |
| M2 POI 与配额 | 统一分类、查询证据、缓存、服务分桶和日账本 | 两算法真实设施闭环，预算与截断语义正确 |
| M3 密度热力 | 真实 BMapGL Canvas、裁剪、平移缩放及生命周期 | 真实地图验证通过，不能只用模拟 SDK 截图 |
| M4 服务场与灰区 | 障碍/入口数据、反向路由、网格三态和灰区 | 数据前置条件、几何及路由测试通过 |
| M5 区间与报告 | 固定分母、图表、问题卡片、共用报告修订 | 地图、统计、报告来源一致，未知不补零 |
| M6 真实验证 | 场景核验、性能记录、配额及运行报告 | 明确通过项、限制和剩余未知，无虚构精度结论 |

原草案 14—20 个工作日仅是初步估算，未充分体现新增服务图和入口准备成本，不作为最终交付承诺。按上述阶段验收推进，M4 不得跳过数据准备而直接以道路 buffer 充当社区覆盖。

### 11.2 逻辑回归用例

- 距离：899、900、999、1000、1001、1100、1101 米；错误和超时不能当作超距。
- 路网：单行步行反向搜索、中途入口、同边直达、桥隧平面交叉、围墙、未知门禁、入口偏移。
- 查询：150 上限、重复页、总数变化、局部失败、圈外设施服务圈内、分类和 UID 冲突。
- 几何：MultiPolygon、孔洞、水体、边界点、null 与空面、相交格和多连通分量。
- 证据：严格 POI 与道路端点证据分开；单点不升级为整格实测；未决入口不直接丢弃。
- 评分：固定分母、未知区间、部分类别不冒充总体、重叠灰区面积不重复计数。
- 配额：重试计数、双算法共享池、午夜、到期、进程重启、取消及详情上限。
- 前端：算法切换和旧报告保留、迟到响应隔离、Marker 不触发选点、图层开关不拉回中心。

### 11.3 可量化验收门槛

1. 每类别 C＋G＋U 与评估域 A 的误差不超过 `max(1 m², A×10⁻⁶)`；灰区不得包含未知格或越出评估域。
2. 固定输入夹具重复运行、不同完成顺序下结果一致；细化网格不能通过点叠加改变服务热力强度。
3. 真实 BMapGL 平移及缩放后，热力定位参考误差不超过 2 个 CSS 像素；裁剪允许 1 像素抗锯齿带。
4. 在记录配置的测试机器、1920×1080 视口、5000 格和 1000 POI 下，已加载图层切换 P95≤200ms，常规拖动平均≥30fps。
5. 反复切换引擎、类别和图层，不出现持续内存增长、重复监听、重复地图实例或静默设施截断。
6. 缺图、缺入口、查询失败和预算耗尽时，系统保留有效圈面及设施，正确显示部分报告或未知。

### 11.4 真实数据验收

仅通过模拟 SDK、Canvas DOM 存在或离线图形测试不算真实热力交付。必须使用真实浏览器 AK、真实 BMapGL 底图和可追溯 POI/分析快照，保存截图、中心、引擎、规则、数据时间和结果哈希。

覆盖普通街区、河桥、封闭小区、路网不完整场景；两算法分别验证。路线核验留出独立样本，不能既参与模型修订又充当独立准确率样本。核验记录 covered/gap/unknown 分布、模型与路线分歧和入口问题，只报告样本支持的结论，不由少量路线宣称整片灰区已实测确认。

性能、真实配额与真实业务准确性分开验收。现有 83 项测试通过属于当前行为基线；实施完成后继续执行后端 pytest、前端 Vitest、TypeScript/Vite 构建及既有 analysis-ui/integration 回归，再运行新增用例和真实地图验收。

最终完成标准：两套算法均形成真实设施检索和地图热力闭环；上海受支持范围生成有来源、有规则、有未知边界的面积诊断和覆盖区间报告，其他地区明确降级，不伪造完整面积或分数。
